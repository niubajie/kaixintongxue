## 2. 值得吸收的五个设计

### 2.1 装配根：依赖在一处创建

Rakazo 的 `run-runtime.ts` 不是业务逻辑，而是**装配根**：读配置 → 构造各提供商 →
拼出 executor → 再拼出后台任务处理器与回收器。业务代码只接收已经装好的依赖。

**我们的现状**：`kaixin_local_go` 的 `main.go` 里 `App` 结构体已经是雏形（store、
catalog、deploy 状态都在这一处创建）；服务端按 `handler → service → repository` 分层。

**吸收约定**（写进编码规则）：

- 外部客户端（数据库、HTTP、模型网关）只在装配处创建，业务代码不得自行 `new`
- 装配根负责把「配置」翻译成「依赖」，业务代码读不到环境变量
- 回收类任务（见 2.2）与业务处理共用同一份装配结果，避免两套配置漂移

### 2.2 运行租约：任务不会永远停在「进行中」

Rakazo 给每次运行分配 `attempt` 与租约：worker 持有租约并定期续租，
另一个进程通过回收器把「过期未续租」的运行判为中断。写入还带 fence，
防止旧 attempt 覆盖新状态。

**我们原来缺什么**：`deploy_runs` 只有 `state`，且只在任务结束时写一次。
进程崩溃或强杀后，界面会永远停留在「进行中」，历史里也没有中断记录。

**已落地（v0.6）**：

| 项 | 实现 |
|---|---|
| 表结构 | `deploy_runs` 增加 `attempt`、`heartbeat_at`、`lease_until`、`error` |
| 领租约 | 任务开始即写 `state=running` 并设置 90 秒租约 |
| 续租 | 执行期间每 30 秒心跳续租 |
| 回收 | 启动时与每次查历史前，把「租约过期仍在 running」的记录标为 `failed`，原因写「任务中断：进程退出或崩溃」 |
| 展示 | 历史页显示尝试次数与中断原因 |

**尚未做**：步骤级断点续装（对应 `SKL-18`）。租约只解决「状态可信」，
不解决「从第 3 步继续」。后者需要每个步骤结束时落 checkpoint，属下一阶段。

### 2.3 计算机抽象：把「在哪台机器上执行」隔离出来

Rakazo 定义了一套 `SandboxProvider` 方法面：`provision`、`isRunning`、`prepare`、
`readFile`、`writeFile`、`listFiles`、`act`、`stop`、`destroy`、`cancelRunWork`，
并由 Docker / Kubernetes / E2B / 桌面本机等多种实现填充。

**我们的取舍**：本机个人场景不需要容器，强行引入容器只会增加安装负担。
但**「计算机抽象」本身有长期价值**：将来做远程执行或云端技能时，接口不用改。

**建议路径**（未落地）：

```
internal/computer
├── computer.go     接口：Exec / ReadFile / WriteFile / List / Cancel
├── local.go        本机实现（当前直接调 exec 的部分收敛进来）
└── remote.go       预留（云端沙箱，暂不实现）
```

引入时机：当出现第二个实现需求时再抽（YAGNI，见 AGENTS 第八节）。

### 2.4 路径收敛与命令守卫

Rakazo 的 `desktop-sandbox-paths.ts` 做三件事：

1. 解析后判断目标是否落在允许的根目录内（`resolve` + `relative`，拒绝 `..` 与绝对路径）
2. Windows 专属校验：设备名（`CON`、`NUL`、`COM1–9`、`LPT1–9`）、保留字符（`<>:"|?*` 与控制字符）、
   结尾的点与空格、UNC 形式 `//`
3. 命令与写入分离：只有静态可判定的命令才放行

**已落地（v0.6）**：`pathsafe.go`

| 函数 | 作用 |
|---|---|
| `validateRelativePath` | 逐段校验：`..`、设备名、保留字符、结尾点空格、UNC |
| `containedIn` | 目标是否在根目录内（含等于根） |
| `safeJoin` | 拼接 + 全套校验，供需要按相对路径取文件的场景 |

已接入资料目录与知识库的全部路径校验（`ensureInside`）。

**明确不吸收**：heredoc / 重定向 / 变量展开级别的 shell 静态解析器（上千行，
且我们不以任意 shell 命令执行安装，风险面不同）。我们只用「白名单命令 + 参数数组」执行。

### 2.5 记忆版本化

Rakazo 的记忆是「文档 + 修订」两张表：保存时用 `expectedRevision` 做乐观锁，
事务隔离级别 Serializable，冲突整体重试；文档可导出为 Markdown 再导入。
**它的检索是文本包含，不是向量语义检索**——不适合直接当复杂知识库用。

**我们的原状**：`kb_documents` + `kb_chunks` 只有「当前版本」，重新索引直接覆盖旧切片。

**已落地（v0.6）**：

| 项 | 实现 |
|---|---|
| 表结构 | `kb_documents` 增加 `revision`；新增 `kb_revisions(doc_id, revision, content, chunks, indexed_at, source)` |
| 写入 | 每次索引在同一事务里重建切片并追加一条修订，`source` 区分 `index` / `rollback` |
| 保留 | 每个文件保留最近 10 个版本，自动裁剪更早的 |
| 回滚 | `POST /api/kb/rollback` 用历史内容重新索引，并记一条 `source=rollback` 的新修订（不覆盖历史） |
| 界面 | 详情显示「第 N 版」，可打开版本历史逐版回滚 |

实测：同一文件索引两次得到 v1/v2，回滚到 v1 后检索命中旧内容、
命中新内容的条数为 0，历史里出现 v3（rollback）。

检索仍用关键词方案（`LIKE` 多词 AND），向量化单独立项。

## 3. 明确不吸收的部分

| 项 | 理由 |
|---|---|
| Electron / TS / Hono / Prisma / oRPC 技术栈 | 已定 Tauri 2 + Go + PostgreSQL，替换代价远大于收益 |
| 多提供商云沙箱（Docker/K8s/E2B/Daytona…） | 个人本机场景用不上，引入后安装体积与故障面都会放大 |
| MCP / Composio / Pipedream 连接器 | 需要第三方账号与网络，我们的技能体系走「软件目录 + 网站寻址」 |
| 团队聊天、多 Bot 协作、Bot 社交 | 产品决策是多成员与云端同步（Q-02），不做 Bot 之间的对话 |
| 复杂 shell 命令解析器 | 见 2.4，风险面不同，维护成本极高 |
| 文件系统级记忆（跨空间共享目录） | 与「私域文档不上传」红线冲突 |

## 4. 目标架构（增量，不推翻现有）

```
本地（kaixin_local_go）
├── main.go              装配根：配置 → store / catalog / 部署状态
├── deploy.go            技能部署执行 + 租约心跳
├── library.go           资料扫描与打开
├── kb.go                知识库切片与检索
├── pathsafe.go          路径收敛（本章 2.4）
├── asr.go               本地语音转写
└── store.go             SQLite：迁移、任务记录、设置

云端（kaixin_server_go）
├── cmd/api/main.go      装配根
└── internal/<模块>/     handler → service → repository

共通约定
├── 运行租约：任务有 attempt 与租约，过期由回收器判中断
├── 日志可追：每次执行独立日志文件，路径落库
└── 审批点：对外发布类动作最后一步必须人工确认
```

## 6. 一句话结论

Rakazo 值得学的是**运行时的可靠性设计**：租约、回收、路径收敛、装配集中。
不值得学的是它的技术栈与云沙箱体系。我们吸收前者（已落两项），保留自己的架构。
