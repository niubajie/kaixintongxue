# 多模型辩论模块 · 方案与技术架构

> 替代原方案中的「多个动漫 IP 开会」。
> 版本 v1.0 ｜ 形态：**多个具名模型，以头像为发言锚点，用文字 + 语音互相辩论，最后给出最优解。**

---

## 0. 为什么这个版本能落地

原方案被否掉的原因不是"开会"这个想法不好，而是**动漫形象**那部分：

| 原设计 | 工作量 | 判定 |
|---|---|---|
| 多角色 Live2D / VRM 渲染 + 口型同步 + 镜头调度 | 动画电影级 | 一个人做不了 |
| 多角色同场景并发语音 | 实时混音 + 打断仲裁 | 远超项目所需 |

新设计把最贵的两块砍掉，保留核心价值：

| 新设计 | 代价 |
|---|---|
| 名字 + 静态头像代替动漫形象 | 占位图，零渲染成本 |
| 头像作为发言锚点（气泡从头像旁伸出） | 纯 CSS 布局 |
| 语音**逐条播放**，不并发 | 不做实时混音 |
| 辩论 2 轮封顶 | 成本可控 |

**"开会"的本质是让不同模型暴露分歧，不是让它们动起来。** 这一点想清楚，成本能降两个数量级。

## 1. 交互形态

```
┌──────────────────────────────────────────────┐
│  问题：3 万预算，先买显卡还是先换整机？        │
├──────────────────────────────────────────────┤
│                                              │
│  ┌──┐  小衡（Qwen）                          │
│  │👤│  我认为应该先换整机。理由是…            │
│  └──┘  ▍（文字流式出现）                      │
│                                              │
│        ┌──┐  小微（DeepSeek）                 │
│        │👤│  我不同意。显卡的边际收益…        │
│        └──┘                                  │
│                                              │
│  ┌──┐  小实（GLM）    ……正在思考              │
│  │👤│                                        │
│  └──┘                                        │
│                                              │
├──────────────────────────────────────────────┤
│  🔊 小衡正在说…  ⏸ 暂停  ⏭ 跳过本条  ⏹ 结束   │
└──────────────────────────────────────────────┘
```

### 四个角色

| 角色 | 职责 | 提示词约束 |
|---|---|---|
| **主张者** | 第一轮给出立场与理由 | 必须给明确结论，不许和稀泥 |
| **质疑者** | 第一轮独立作答，第二轮专攻主张者的薄弱处 | 必须指出具体缺陷，不许泛泛而谈 |
| **补充者** | 第一轮独立作答，第二轮补盲区 | 必须提供前两人没说到的角度 |
| **裁判** | 归纳共识、标注分歧、给出推荐 | 必须选边，不许"各有优劣"了事 |

**裁判不许和稀泥，是这套设计的成败关键。** 否则用户看完只觉得"说了半天等于没说"。

## 2. 三个必须接受的现实约束

### 2.1 语音是逐条播放，不是同时说话

"互相辩论"在**逻辑层**成立（第二轮能看到第一轮全部内容），在**听觉层**是串行的。

原因：

- 多个 TTS 同时播放会糊成一团，用户听不清任何一方
- 并发语音需要实时混音 + 打断仲裁，属于会议软件级能力
- 逐条播放配合"跳过本条"按钮，体验反而更可控

**这条要写进产品文案，不要让用户以为是真·多人语音会议。**

### 2.2 辩论轮数硬上限 2 轮

每多一轮，成本近似翻倍，延迟增加 6–8 秒。2 轮已经足够暴露分歧：

```
第 1 轮：各自立论（并行，互不可见）→ 暴露初始立场差异
第 2 轮：看到别人观点后反驳（并行）→ 暴露真实分歧点
裁判  ：归纳 → 得出结论
```

3 轮以上，模型会开始互相附和，收益递减。

### 2.3 不是每次提问都开会

开会成本是单模型的 **4–9 倍**，延迟是 **3–4 倍**。必须显式触发。

## 3. 编排架构

```
用户提问
   │
   ├─ 路由判定（单模型 / 开会）
   │     ├─ 用户手动点「开会」            → 直接进会议
   │     └─ 系统判定（问题含比较/权衡/推荐）→ 提示"是否让 3 个模型辩论一下"
   │
   ├─ 参与者装配
   │     ├─ 选 3 个模型（反同质化规则）
   │     ├─ 分配名字 / 头像 / 音色
   │     └─ 分配角色（主张 / 质疑 / 补充）
   │
   ├─ 第 1 轮：并行调用 3 个模型（互不可见）
   │     └─ 每个：流式文字 → 落库 → 触发 TTS
   │
   ├─ 第 2 轮：把 3 份立论拼进上下文，再并行调用 3 个模型
   │     └─ 限 200 字反驳
   │
   ├─ 裁判：输入 6 条发言 → 输出结构化结论
   │
   └─ 收尾：写 usage_records、生成结论语音、推送 verdict 事件
```

### 并行是硬要求

6 次调用如果串行，延迟 40 秒以上，用户早跑了。并行后第 1 轮 ≈ max(各模型) ≈ 6–8 秒。

用 Go 的 `errgroup` + 单模型超时 20 秒控制。

## 4. 触发策略

| 触发方式 | 说明 |
|---|---|
| **手动**（主） | 输入框旁一个「多模型辩论」按钮，用户自己决定 |
| **建议**（辅） | 识别到比较类问题（"选哪个""值不值""该不该"）时，轻提示一次 |
| **自动** | ❌ 不做。用户不知道钱是怎么烧掉的，会骂人 |

**默认关闭自动触发。** 让用户为"多花 5 倍成本"这件事做一次显式选择。

---

## 5. 参与者选择（反同质化）

### 规则

1. **同一 provider 最多 1 个**——4 个 Qwen 变体辩论，等于自己跟自己吵
2. 优先不同家族：DeepSeek / Qwen / GLM / Claude / GPT 各取其一
3. 能力档位错开：1 个旗舰 + 2 个性价比，避免全用最贵的
4. 至少 1 个中文强的（你的用户在国内）

### 默认组合

| 座位 | 角色 | 模型建议 | 头像 | 音色 |
|---|---|---|---|---|
| 1 | 主张者 | Qwen（中文稳） | 小衡 | 男声·沉稳 |
| 2 | 质疑者 | DeepSeek（推理强） | 小维 | 女声·清亮 |
| 3 | 补充者 | GLM（视角广） | 小实 | 男声·轻快 |
| 4 | 裁判 | 与三者都不同家族 | — | 旁白 |

**裁判不参与辩论、没有头像、不出现在气泡列表里**，只在最后出一张结论卡。

## 6. 数据模型

新增 3 张表，不动现有 `conversations / messages`。

```sql
debate_sessions
  id, uuid, user_id, conversation_id
  question            TEXT
  status              queued | running | finished | failed | cancelled
  rounds              SMALLINT      -- 实际轮数，最多 2
  verdict_text        TEXT          -- 结论正文
  verdict_json        JSONB         -- { conclusion, reasons[], disagreements[], confidence }
  total_cost_cents    BIGINT
  error_message       TEXT
  started_at, finished_at, created_at

debate_participants
  id, session_id
  model_uuid          UUID          -- 关联 models 表
  display_name        TEXT          -- 小衡 / 小维 / 小实
  avatar_key          TEXT          -- avatars/a1.png，指向客户端本地资源
  voice_key           TEXT          -- 音色标识
  stance              proponent | challenger | supplementer | judge
  seat_index          SMALLINT
  status              pending | running | done | failed | skipped

debate_utterances
  id, session_id, participant_id
  round_no            SMALLINT      -- 1 / 2；裁判为 0
  kind                opening | rebuttal | verdict
  content_text        TEXT
  audio_url           TEXT          -- 对象存储地址，可为空
  audio_status        pending | ready | failed | disabled
  tokens_in, tokens_out, cost_cents
  created_at
```

**要点：**

- `avatar_key` 存的是**资源键**不是 URL——头像打包在客户端，换头像不用改数据
- `audio_url` 可为空：用户关掉语音时就不生成，省 TTS 钱
- `verdict_json` 结构化，前端才能渲染成结论卡而不是一段大白话

## 7. 接口契约

```
POST   /api/v1/debates              创建会议（立即返回 id，后台异步跑）
GET    /api/v1/debates/{id}         查状态与完整结果
GET    /api/v1/debates/{id}/stream  SSE 实时事件流
POST   /api/v1/debates/{id}/cancel  取消
GET    /api/v1/debate-presets       可选：预置参与者组合
```

### SSE 事件

```
session.started      { sessionId, participants[] }
round.started        { round }
utterance.started    { utteranceId, participantId, name, seatIndex }
utterance.delta      { utteranceId, text }        // 流式文字
utterance.finished   { utteranceId, tokens, costCents }
utterance.audio      { utteranceId, audioUrl }
round.finished       { round }
verdict.ready        { conclusion, reasons[], disagreements[], confidence }
participant.failed   { participantId, reason }
session.finished     { totalCostCents }
```

**文字先到先显示，语音后补。** 不要等语音合成完再显示文字，那样前 10 秒是空白。

## 8. 客户端渲染

### 头像作为发言锚点

```css
.debate-seat { display: flex; gap: 12px; align-items: flex-start; }
.debate-seat.right { flex-direction: row-reverse; }   /* 交替左右，制造对话感 */

.speech-bubble {
  position: relative;
  border-radius: 14px;
  background: var(--surface);
}
/* 气泡的小尖角从头像方向伸出 —— 这就是"发言位置起点" */
.speech-bubble::before {
  content: "";
  position: absolute;
  left: -7px; top: 14px;
  border: 7px solid transparent;
  border-right-color: var(--surface);
}
.debate-seat.right .speech-bubble::before {
  left: auto; right: -7px;
  border-right-color: transparent;
  border-left-color: var(--surface);
}
```

- 座位交替左右，方向感更强
- 未发言者头像降饱和度，发言者高亮 + 轻微呼吸动画
- 思考中显示三个点，不显示"正在加载"

### 语音播放队列

```
每条 utterance 的音频进入队列 → 顺序播放
  播放中：正文同步高亮当前句
  播放完：自动播下一条
  用户点"跳过"：停止当前，播下一条
  用户点"暂停"：暂停队列
  用户点"结束"：清空队列，直接跳到结论卡
```

**关键：用户随时能跳过。** 8 条语音全听完要 3 分钟，大部分人听 2 条就想看结论。

## 9. 成本与延迟预算

按 3 个辩论者 × 2 轮 + 1 个裁判 = **7 次模型调用 + 6 条 TTS**。

| 项 | 用量 | 国内模型 | 旗舰模型 |
|---|---|---|---|
| LLM 输入 | 约 1.4 万 token | ¥0.02 | ¥0.5 |
| LLM 输出 | 约 4 千 token | ¥0.02 | ¥0.6 |
| **TTS** | 6 条约 4 分钟 | **¥1.5–4** | 同左 |
| **合计** | | **约 ¥1.6–4.1** | **约 ¥2.1–4.7** |

**结论：语音成本是模型调用的 50–100 倍。**

所以默认策略：

| 模式 | 说明 | 成本 |
|---|---|---|
| **文字模式**（默认） | 只出文字，不合成语音 | ¥0.05–1.1 |
| **结论配音** | 只给最终结论配一条语音 | + ¥0.3–0.8 |
| **全程语音** | 6 条全配 | + ¥1.5–4 |

**建议默认"文字模式 + 结论配音"。** 辩论过程靠读（速度快），结论靠听（省事）。

### 延迟

| 阶段 | 耗时 |
|---|---|
| 第 1 轮（并行） | 6–8 秒 |
| 第 2 轮（并行） | 6–8 秒 |
| 裁判 | 3–5 秒 |
| **文字全部完成** | **约 18–22 秒** |
| 首条语音可播 | 再 +1.5 秒 |

**18 秒以上必须有进度反馈**：显示第几轮、谁在说话、已完成几条。否则用户以为卡死。

## 10. 降级与失败处理

| 情况 | 处理 |
|---|---|
| 单个模型超时（20s） | 跳过该参与者，其余继续；结论卡标注"缺少 X 的观点" |
| 参与者 < 2 成功 | 退化为单模型直答，提示"辩论失败，已改为直接回答" |
| 裁判失败 | 取最长的一条立论作为结论，标注"未融合" |
| TTS 失败 | 静默降级为纯文字，不报错 |
| 用户中途取消 | 立即停止后续调用，已生成的保留可看 |
| 全流程超时（60s） | 强制收尾，返回已有内容 |

**原则：宁可少一个观点，也不能让用户看到一片空白。**

## 11. 合规：私域内容不能开会

这是必须硬拦的一条。

```
若会话包含私域资料：
  且 所有参与者 region != 'local'
  → 拒绝，提示「私域内容仅支持本地模型，无法多模型辩论」
```

理由：辩论意味着把私域内容同时发给 3 家不同的模型厂商，**数据出境面扩大 3 倍**。这与产品"私域不出本机"的承诺直接冲突。

替代方案：允许启动**全本地模型辩论**（都跑 Ollama），但速度和能力会明显下降，作为降级选项提供。

## 12. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| **模型同质化**：三家结论雷同，辩论毫无意义 | ★★★★★ | 强制不同 provider + 差异化角色提示词 + 用"必须找出对方一个具体缺陷"约束 |
| **裁判和稀泥**：结论变成"各有优劣" | ★★★★★ | 提示词要求必须选边并给置信度；输出结构强制含 `disagreements[]` |
| 成本被刷：反复点开会 | ★★★★☆ | 每日配额（免费 3 次/天），单次预算上限 |
| 延迟劝退：18 秒没有反馈 | ★★★★☆ | 分阶段进度 + 流式文字 + 先出第一条 |
| 语音听到一半想跳过 | ★★★☆☆ | 一键跳过 + 默认只给结论配音 |
| 并发调用触发上游限流 | ★★★☆☆ | 同一 provider 串行、跨 provider 并行；失败重试 1 次 |

## 13. 分阶段

| 阶段 | 内容 | 说明 |
|---|---|---|
| **D1** | 3 模型 × 1 轮 + 裁判，纯文字，无 SSE（轮询） | 验证"多模型是否真的会产生分歧" |
| **D2** | 加第 2 轮反驳 | 分歧质量明显提升才继续 |
| **D3** | SSE 流式 + 头像锚点 UI | 体验层 |
| **D4** | 结论配音（只配结论） | 成本最低的语音形态 |
| **D5** | 全程语音 + 播放队列 + 跳过 | 视 D4 数据决定 |

**D1 是关键验证点**：如果 3 个模型给出几乎一样的答案，这个功能就没有存在价值，及时止损。

---

## 14. 三句话总结

1. **头像只是锚点，不是动画**——省掉整个 Live2D/VRM 技术栈。
2. **语音逐条播，不并发**——省掉实时混音，且体验更可控。
3. **裁判必须选边，模型必须不同源**——前者决定结论有没有用，后者决定辩论有没有意义。
