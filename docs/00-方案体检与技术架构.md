## 一、产品本质

你描述的不是一个聊天软件，而是一个 **实时多模态智能体平台**，核心是四件事：

1. **多模型编排** —— 单个或 N 个模型出答案，再融合
2. **多模态双向交互** —— 文字 / 语音 / 摄像头画面 / 生成视频，且可打断
3. **私域知识增强** —— 本地资料 + 公域资料，检索后融合回答
4. **过程化管理** —— 学习、目标、实践三类场景的规划与记录

这四件事在技术上属于 **四个不同的专业领域**（LLM 工程、实时音视频、多模态视觉、知识库检索）。一个人做完，工作量在 **8～15 人年**量级。

所以结论不是"能不能做"，而是 **"先做哪一块，才不至于做一半放弃"**。

## 三、三个必须先解决的矛盾

### 矛盾一：私域"存本地" vs "三端可用"

你的要求是：私域资料存本地电脑，但电脑、网页、手机、平板都能用。

**这两条天然冲突**——手机和网页访问不到你电脑上的硬盘。

三个可选方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 私域只在桌面端** | 手机/网页只能查公域 + 云端个人库 | 实现最简单、最安全 | 手机端体验不完整 |
| **B. 桌面端做本地服务 + 中继** | 电脑跑本地知识库服务，通过加密隧道供其他端访问 | 三端一致 | 电脑必须开机；NAT 穿透复杂 |
| **C. 加密分片上传** | 本地加密后上传云端，密钥留在本地 | 三端可用 | 密钥在客户端 = 防不住逆向；与你"防泄密"目标冲突 |

> **建议：先做 A，把 B 作为第二阶段。C 不要做**——它给人"安全"的错觉，实际是自欺欺人。

关于"防泄密"，真正有效的措施是这几条，不是"存本地"本身：

1. 本地库整库加密，密钥由 Windows DPAPI 保护（绑定当前用户）
2. 检索只返回相关片段，**不提供"导出全部"接口**
3. 每次读取写审计日志（时间、问句、命中片段 ID），本地可见
4. 调用云模型时只发送必要片段，且选**零保留（Zero Retention）条款**的服务商
5. 检索结果加水印，便于追溯泄露源

> 注意：真正防不住的是"用户自己截图/复制"。产品层面的目标是**防批量外泄**，不是防单次泄露。这个预期要提前对齐。

### 已决策：砍掉小程序端

**v1.1 决策：不做小程序。** 剩余三端（Windows 桌面 / 网页 / 手机+平板 App）全部由同一套 React 代码产出。

这个决策砍掉了两样东西，收益很直接：

| 砍掉的东西 | 收益 |
|---|---|
| Taro / uni-app 这条独立构建链 | 前端从"两套框架"变成"一套代码"，学习和维护成本减半 |
| 小程序主体、类目审核、小程序域名备案 | 少一条发布链路，少一堆合规工作 |

**代价也要知道：**

- 失去微信生态的流量入口（分享裂变、搜一搜、附近的小程序）
- 手机端第一次使用要下载 App 或打开网页，转化路径比小程序长
- 网页端仍然需要域名 + ICP 备案 + HTTPS

**顺带说明：关于实时语音双工**

技术障碍不是资质，是**回声消除（AEC）**。没有 AEC，"边说边听"会把自己播放的声音录回去，导致自打断甚至死循环。

- 桌面 / 手机 App：可用系统级 AEC（WebRTC 的 `echoCancellation: true`），真双工可行
- 网页：浏览器 WebRTC 同样支持 AEC，可行
- 折中方案：让用户戴耳机、播放时暂停录音（退化为半双工）、能量门限 + 服务端 VAD 兜底

还有一个前提：**你的需求 C（拍主板并标注芯片位置）不需要视频流。** 拍一张高清照片做识别和标注，比实时视频更清晰、更省流量、延迟更低。

### 矛盾三：视频生成 vs 成本

按爆款结构生成视频，单条 60 秒的成本在 **¥10–100** 区间（取决于模型和分辨率），而且质量不稳定、需要多次重试。

如果免费用户每天用一次，1000 个用户 = 每月 **¥30 万起**。

**结论：视频生成不做第一版。** 如果将来要做：

- 只对**付费用户**开放
- 按次计费，价格里含 3 倍成本冗余
- 结果**缓存复用**，同类问题直接返回已有视频
- 先用"预制视频片段 + 文字讲解"替代（成本几乎为零）

### 各层职责

| 层 | 职责 | 关键设计 |
|---|---|---|
| 端 | 采集、渲染、交互 | 能力探测，向上报"我支持什么" |
| 接入层 | 统一入口 | 鉴权、限流、审计、SSE/WS 长连接 |
| 编排层 | **产品的大脑** | 技能选择、多模型融合、工具调用 |
| 模型网关 | **唯一能调外部模型的地方** | 统一接口、路由、降级、计费、留痕 |
| 多模态 | 语音/视觉/视频/形象 | 每个能力独立可插拔 |
| 知识库 | 检索增强 | 公私域混合检索 + 重排 |
| 场景引擎 | 三场景的业务逻辑 | 统一数据模型 |
| 数据层 | 持久化 | 业务库与向量库分离 |

### 两条铁律

1. **所有模型调用必须经过"模型网关"**，禁止业务代码直接调某个厂商 API。否则你换模型、控成本、做降级时会疯掉。
2. **技能（Skill）是唯一的产品单元**，不是页面。一个新能力 = 新增一个技能包，不改主流程。

## 七、数据模型核心

三场景（学习/目标/实践）**不要建三套表**，用一套抽象：

```
Objective（目标对象，type = learning | goal | practice）
  ├─ 标题、描述、状态、起止时间、关联技能
  ├─ Milestone（里程碑）
  ├─ Plan（计划，可按周/阶段）
  ├─ Task（任务，可勾选）
  └─ Session（一次执行记录：时间、耗时、内容、附件、复盘）
        └─ Log（过程中的事件、心得、错题）
```

核心表清单：

| 表 | 说明 |
|---|---|
| `user` / `device` | 账号、设备（端类型、能力位） |
| `workspace` | 个人空间（预留多租户） |
| `conversation` / `message` | 会话与消息（含 modality、附件引用） |
| `skill` / `skill_binding` | 技能定义与用户启用关系 |
| `model_provider` / `model_route` | 模型供应商、路由规则、价格 |
| `knowledge_base` / `document` / `chunk` | 知识库、文档、切片（含 `scope: public/private`） |
| `objective` / `milestone` / `plan` / `task` / `session` / `log` | 三场景统一模型 |
| `media_asset` | 图片/音频/视频元数据 |
| `annotation` | 视觉标注结果（坐标、类型、关联消息） |
| `quota` / `usage_record` | 配额与用量（按能力计费的基础） |
| `audit_log` | 审计（私域读取、导出、权限变更） |

**统一字段规范**（所有表）：

```
id            BIGINT 主键自增；对外用 uuidv7
created_at    timestamptz  默认 now()
updated_at    timestamptz  自动更新
deleted_at    timestamptz  软删除，NULL 表示未删
```

## 八、成本模型（必须现在就想清楚）

| 能力 | 单次成本量级 | 说明 |
|---|---|---|
| 文字问答（单模型） | ¥0.001 – 0.01 | 便宜 |
| 多模型融合（3+1） | ¥0.01 – 0.05 | 成本 ×4，延迟 ×2 |
| 图像理解 | ¥0.01 – 0.1 / 张 | 看分辨率 |
| 语音对话 | ¥0.2 – 1 / 分钟 | ASR + LLM + TTS |
| 实时视频对话 | ¥0.5 – 2 / 分钟 | 含带宽 + 模型 |
| 爬取补充知识库 | ¥0.1 – 1 / 千页 | 含清洗与向量化 |
| 视频生成 | ¥10 – 100 / 条 | **不可免费** |
| 头像与语音合成 | TTS 约 ¥0.3–1 / 分钟；头像为静态资源，零渲染成本 | 语音成本远高于模型调用 |

**必须做的三件事：**

1. **每个能力都有配额**，按用户等级分配（免费/付费/企业）
2. **每次调用写 `usage_record`**，可追溯到具体用户和会话
3. **成本超阈值自动降级**（多模型融合 → 单模型；实时视频 → 语音）

不做这三件，产品上线第一个月就会因为账单崩掉。

## 十、风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围过大导致做不完 | ★★★★★ | 严格按 MVP 砍功能，每期只上一类端 |
| 实时音视频自研 | ★★★★★ | 一律用云服务（TRTC/Agora/Realtime API） |
| 视频生成成本失控 | ★★★★☆ | 第一版不做；做则付费 + 缓存 |
| 视觉标注精度不达预期 | ★★★★☆ | 加"用户点选辅助"，把定位问题转为确认问题 |
| 私域数据泄露 | ★★★★★ | 本地加密 + 无批量导出 + 审计日志 + 零保留 API |
| 移动端打包复杂度 | ★★★☆☆ | 先做 H5，验证有需求再上 Capacitor；不要一上来做原生 |
| 模型 API 涨价/下线 | ★★★☆☆ | 模型网关做多供应商抽象，随时切换 |
| 版权风险（爬取/生成） | ★★★☆☆ | 只用允许的来源；生成内容加水印 |

## 十一、给你的三个提醒

1. **先做"能用的一个场景"，不要做"完整的四个端"。** 你的方案最大的敌人不是技术难度，是范围。
2. **实时音视频、视频生成这两样，全部用现成服务，一行自研代码都不要写。** 动漫形象已取消，改为「头像 + 语音」，直接省掉整个 Live2D / VRM 技术栈。
3. **第一天就写 `usage_record` 和配额。** 后补的话，你得重算所有历史账单。
