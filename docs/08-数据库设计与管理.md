## 0. 一句话

**服务器用 PostgreSQL 存业务，用户电脑用 SQLite 存私域，两套 DDL 字段语义必须对齐。**

---

## 1. 双库架构

| 库 | 位置 | 存什么 | 备份 | 谁能访问 |
|---|---|---|---|---|
| **PostgreSQL 18** | 服务器 | 账号、会话、技能、目标、用量、公域知识库、模型目录 | 每日全量 + 归档 | 仅后端服务 |
| **SQLite** | 用户电脑 | 私域文档、切片、向量索引、本地会话 | 用户自己负责 | 仅本机应用 |

**私域数据永不上传**，这是产品承诺的技术兑现点（见 `docs/06` 第 5 节）。

### 1.1 两个库共有的表

| 表 | PostgreSQL | SQLite |
|---|---|---|
| `documents` | 公域文档 | 私域文档 |
| `chunks` | 带 `vector(1024)` | 带 BLOB 向量 |
| `conversations` / `messages` | 云端会话 | 本地会话 |

### 1.2 类型对齐表（强制）

| 语义 | PostgreSQL | SQLite |
|---|---|---|
| 主键 | `BIGSERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` |
| 对外 ID | `UUID` | `TEXT` |
| 时间 | `TIMESTAMPTZ` | `TEXT`（ISO 8601，UTC） |
| 结构化字段 | `JSONB` | `TEXT`（JSON 字符串） |
| 数组 | `TEXT[]` | `TEXT`（JSON 数组） |
| 向量 | `vector(1024)` | `BLOB`（Float32 小端拼接） |
| 金额 | `BIGINT`（分） | `INTEGER`（分） |
| 布尔 | `BOOLEAN` | `INTEGER`（0/1） |

**禁止使用只有一边支持的特性**（比如 PG 的生成列、SQLite 的动态类型）。否则同步逻辑会分裂。

## 2. 本地开发配置

### 2.1 docker-compose 逐项说明

```yaml
postgres:
  image: pgvector/pgvector:pg18   # ① 官方 postgres 镜像不含 pgvector
  environment:
    POSTGRES_USER: app
    POSTGRES_PASSWORD: app_dev_password
    POSTGRES_DB: agent
    POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"  # ②
  ports: ["5432:5432"]
  volumes: [pgdata:/var/lib/postgresql/data]            # ③
  healthcheck:                                          # ④
    test: ["CMD-SHELL", "pg_isready -U app -d agent"]
```

| 编号 | 为什么 |
|---|---|
| ① | 向量检索要 `CREATE EXTENSION vector`，官方镜像装不了 |
| ② | UTF8 保证中文不乱码；`locale=C` 让排序可预测（见第 9 节） |
| ③ | 命名卷，`docker compose down` 不丢数据；`down -v` 才清空 |
| ④ | 后端启动可能早于数据库就绪，靠 healthcheck 判断 |

### 2.2 三条约定

1. **镜像不用 `latest`**，锁到具体大版本，避免某天自动升级炸掉
2. 如果 `pg18` 标签拉不到，退到 `pgvector/pgvector:pg17`，功能一致
3. 本地密码可以写死，生产必须走环境变量

## 3. 生产配置（2 核 2G 起步机）

### 3.1 必须调的参数

默认配置是按 4 GB 以上内存写的，2 GB 机器直接跑会被 OOM Killer 干掉。

```conf
# postgresql.conf
shared_buffers = 256MB          # 默认 128MB；不超过内存 1/4
effective_cache_size = 512MB
work_mem = 4MB                  # 每个排序/哈希操作都吃，默认够用别调大
maintenance_work_mem = 64MB
max_connections = 50            # 默认 100，每连接有固定内存开销
```

### 3.2 必须加 swap

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

**没有 swap 的 2 GB 机器，一次慢查询就是一个进程被杀。**

### 3.3 必须关的默认值

| 项 | 设置 | 原因 |
|---|---|---|
| `listen_addresses` | `'localhost'` | 数据库不暴露公网 |
| 防火墙 | 不开放 5432 | 同上 |
| `ssl` | 开启，应用侧 `sslmode=require` | 即使内网也加密 |
| 超级用户 | 应用不使用 `postgres` 账号 | 最小权限 |

### 3.4 账号划分

| 账号 | 权限 | 用途 |
|---|---|---|
| `app_rw` | 表 CRUD，无 DDL | 后端服务 |
| `app_migrate` | 有 DDL | 只跑迁移 |
| `app_readonly` | 只读 | 报表 / 排障 |

## 4. 连接池

### 4.1 现在的配置

`internal/db/db.go`：

```go
MaxConns          = 20
MinConns          = 2
MaxConnLifetime   = time.Hour
MaxConnIdleTime   = 30 * time.Minute
HealthCheckPeriod = time.Minute
```

**这 20 是拍脑袋定的，要改成环境变量。**

### 4.2 计算公式

```
PG 可用连接数 = max_connections − 保留（运维/监控/迁移，取 10）
每实例 MaxConns ≤ 可用连接数 ÷ 实例数
```

**示例**（`max_connections = 50`）：

| 实例数 | 可用 | 每实例 MaxConns | 建议取值 |
|---|---|---|---|
| 1 | 40 | 40 | 30（留余量） |
| 3 | 40 | 13 | 12 |
| 5 | 40 | 8 | 8 |

### 4.3 实例多了怎么办：上 PgBouncer

```
应用（MaxConns 20 × 5 实例 = 100）→ PgBouncer（到 PG 只保持 15）→ PG
```

**一个坑必须注意**：PgBouncer 的 `transaction` 模式不支持预处理语句，而 pgx 默认走扩展协议。两种解法：

| 解法 | 做法 |
|---|---|
| 应用侧降级 | DSN 加 `default_query_exec_mode=simple_protocol` |
| PgBouncer 侧支持 | 设 `max_prepared_statements = 100` |

不加这一条，上线会出现莫名其妙的 `prepared statement already exists` 报错。

## 5. 迁移管理

### 5.1 现状的问题

现在靠 `psql -f 0001_init.sql` 手动执行，**没有版本记录表**。生产库跑到第几版、下次该执行哪个，全靠人记。

### 5.2 改用 golang-migrate

```
server/migrations/
├── 000001_init.up.sql
├── 000001_init.down.sql
├── 000002_vector.up.sql
└── ...
```

```bash
migrate -path db/migrations -database "$DATABASE_URL" up
migrate -path db/migrations -database "$DATABASE_URL" down 1
```

执行后自动维护 `schema_migrations` 表，记录已应用版本。

### 5.3 三条铁律

| 规则 | 原因 |
|---|---|
| 已应用的迁移文件**不准改** | 改了不会重跑，造成环境不一致 |
| 每个迁移都要有 `down` | 出问题要能回滚 |
| 破坏性变更分两步 | 先加新列 → 发版 → 删旧列，不要一步到位 |

**"先加后删"这条最容易被忽略**：直接 `DROP COLUMN` 会让旧版本实例瞬间报错。

## 6. 备份与恢复

### 6.1 备份策略

| 项 | 做法 |
|---|---|
| 频率 | 每日 02:00 全量 |
| 格式 | `pg_dump -Fc`（压缩、可选择性恢复） |
| 保留 | 本地 7 天 + 对象存储 30 天 |
| 异地 | 至少一份不在同一台机器上 |
| WAL | 自建库开归档；云 RDS 用自带时间点恢复 |

```bash
pg_dump -Fc -h localhost -U app_migrate agent > backup_$(date +%F).dump
```

### 6.2 恢复

```bash
pg_restore -d agent_restore --clean --if-exists backup_2026-11-16.dump
```

### 6.3 一条硬规定

> **每月演练一次恢复。没演练过的备份等于没有备份。**

把恢复出来的库连到一个临时实例，跑一遍 `/healthz` 和几条关键查询。这一步花 20 分钟，能救一次数据事故。

## 7. 数据保留策略

不带清理的表会无限增长，半年后磁盘就满了。

| 表 | 增长速度 | 保留策略 |
|---|---|---|
| `usage_records` | 每次模型调用一条 | 明细保留 90 天，之后按月汇总到 `usage_daily` |
| `audit_logs` | 每次敏感操作一条 | 保留 180 天（合规要求），之后归档冷存储 |
| `messages` | 每轮对话 2 条 | 保留 1 年，之后归档 |
| `debate_utterances` | 每次辩论 6 条 + 结论 | 保留 90 天 |
| `annotations` | 每次标注一批 | 跟随 `messages` |

实现方式：`asynq` 定时任务，每天 03:00 跑一次归档 + 删除。

**注意**：删除要分批（每批 1000 行），一次性删百万行会锁表。

## 8. 扩容触发条件

| 现象 | 触发条件 | 动作 |
|---|---|---|
| 连接数紧张 | 峰值连接 > `max_connections × 70%` | 上 PgBouncer |
| 慢查询 | P99 > 500ms 且占比 > 1% | 看执行计划、加索引 |
| 单表过大 | > 1000 万行 | 按月分区 |
| 读压力大 | 主库 CPU 持续 > 70% 且以读为主 | 加只读副本 |
| 写压力大 | WAL 生成速率持续高 | 分表 / 评估换架构 |
| 磁盘不够 | 使用率 > 80% | 扩容 + 清理历史 |

**在触发之前不要做这些优化。** 索引和分区都是有成本的，没到瓶颈就先别动。

## 9. 编码、时区与排序

| 项 | 设置 | 说明 |
|---|---|---|
| 编码 | UTF8 | 中文不乱码 |
| 排序规则 | `locale=C` | 让比较行为可预测，**不依赖系统 locale** |
| 时区 | 全部 `TIMESTAMPTZ`，存 UTC | 展示时前端转本地 |
| 中文排序 | **应用层做** | `locale=C` 下 `ORDER BY` 是字节序，不是拼音 |

如果需要按拼音排序，两条路：

1. 应用层拿全量后排序（数据量小可行）
2. 装 `pg_trgm` 或 `zhparser` 扩展（需要改镜像，云 RDS 多数支持）

**当前方案选 1**，因为暂时没有按标题排序的需求。

## 10. 索引策略

已有索引（见 `0001_init.sql`）：

| 表 | 索引 | 用途 |
|---|---|---|
| `objectives` | `(user_id, type, status) WHERE deleted_at IS NULL` | 列表查询 |
| `messages` | `(conversation_id, created_at)` | 会话回放 |
| `usage_records` | `(user_id, created_at DESC)` | 用量统计 |
| `chunks` | `(document_id, ordinal)` | 按文档取切片 |

原则：

1. **每个查询都要走索引**，`EXPLAIN ANALYZE` 验证
2. 软删除的表用**部分索引**（`WHERE deleted_at IS NULL`），索引更小更快
3. **不要给每个字段都建索引**，写入会变慢
4. HNSW 向量索引等数据量到 10 万条再建（见 `0002_vector.sql` 注释）

## 11. 本地 SQLite：打包、落盘与初始化

### 11.1 引擎与数据文件是两样东西

| 东西 | 是什么 | 进安装包的方式 |
|---|---|---|
| **SQLite 引擎** | 一个库（几十万行 C 代码） | **编译进二进制**，不是单独文件 |
| **数据库文件 `.db`** | 用户的数据 | **不打包**，首次运行时创建 |

**引擎决定"能不能"，`.db` 决定"存在哪"，CRUD 代码决定"存什么"。**

### 11.2 引擎怎么进包

按 `docs/06` 的规矩，本地库由 **Go sidecar 独占管理**，前端不直接碰 SQLite：

```
Tauri 壳 → HTTP → Go sidecar (agent-server.exe) → SQLite
```

推荐驱动：**`modernc.org/sqlite`（纯 Go 实现，不需要 CGO）**

| 优势 | 说明 |
|---|---|
| 零额外文件 | 编译进 `agent-server.exe`，安装目录不多一个 dll |
| 交叉编译简单 | 不需要 C 工具链 |
| 体积 | sidecar 20 MB → 约 24 MB |

**两个不要用的方案：**

| 方案 | 为什么不行 |
|---|---|
| `mattn/go-sqlite3` | 需要 CGO，Windows 交叉编译很痛苦 |
| `tauri-plugin-sql` | 前端直连本地库，破坏 `docs/06` 的安全边界 |

### 11.3 文件放哪

```
✅ %LOCALAPPDATA%\Kaixin\data\app.db
❌ C:\Program Files\Kaixin\data\app.db
```

放安装目录的三种后果：

| 问题 | 后果 |
|---|---|
| Program Files 需要管理员写权限 | 普通用户报 `readonly database` |
| 卸载时一起删掉 | **用户数据丢失** |
| 多用户共用一台电脑 | 数据互相串 |

### 11.4 schema 从哪来：编译进二进制

不打包 `.db`，改打包**迁移脚本**：

```go
//go:embed migrations/*.sql
var migrationFS embed.FS
```

首次启动流程：

```
1. 检查 %LOCALAPPDATA%\Kaixin\data\ → 没有就建
2. 打开 app.db（不存在会自动创建空文件）
3. 读 schema_version
   ├─ 0        → 依次执行全部迁移（建库）
   ├─ 落后     → 只跑缺失的迁移
   └─ 等于/超前 → 跳过
4. 任一步失败 → 备份现有文件并提示
```

### 11.5 一次"保存"的完整链路

```
[1] 用户点保存
[2] 前端调 bridge / HTTP
[3] Go handler   解析参数
[4] Go service   业务校验
[5] Go repository  执行 INSERT
[6] SQLite 引擎  写 app.db（先 WAL，再落盘）
[7] 返回新 id → 界面刷新
```

**第 6 步才是真的存下来**，它依赖下面五样东西：

| # | 要素 | 缺了会怎样 |
|---|---|---|
| 1 | 引擎（编译进 sidecar） | 编译期就报错，压根没这功能 |
| 2 | `.db` 文件 | 每次启动都是空的 |
| 3 | CRUD 代码 | 有库但没内容 |
| 4 | 可写目录 | 报 `attempt to write a readonly database` |
| 5 | 迁移与版本 | 升级后旧库打不开 |

### 11.6 三个常见误解

| 误解 | 实际 |
|---|---|
| "打包了就能自动保存" | 得写 CRUD，一行 SQL 不会自己产生 |
| "`.db` 会自动出现" | 要主动打开才创建，且必须指定路径 |
| "放安装目录就行" | Program Files 普通用户写不了 |

### 11.7 参数与备份

| 项 | 设置 | 说明 |
|---|---|---|
| 日志模式 | `PRAGMA journal_mode=WAL` | 读写并发不互相阻塞 |
| 同步级别 | `PRAGMA synchronous=NORMAL` | 性能与安全的平衡点 |
| 备份 | `VACUUM INTO 'backup.db'` | 比直接拷文件安全 |
| 迁移失败 | 保留 `app.db.bak` 再重试 | 可回退 |
