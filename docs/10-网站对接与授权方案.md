# 网站对接与授权方案

> **状态：相关功能已于 2026-11-20 下线，本文档仅作历史留档。**
>
> 版本 v1.0 ｜ 解决的问题：技能一旦「要用到某个网站」，就必须回答三件事——
> **打开哪个页面、怎么拿到授权、数据从哪里来。**
>
> 本文把这个过程落到**具体页面**，而不是停在"需要登录"这种模糊描述。

---

## 0. 一句话

**每个网站都要登记一张「页面地图」。** 程序只做两件事：把用户送到正确的页面，以及在页面/接口上完成动作。绝不替用户填密码、点同意。

---

## 1. 先把交互分成三类

| 类型 | 目的 | 落点 | 例子 |
|---|---|---|---|
| **Auth 授权** | 证明"我是这个账号的主人" | 平台授权页 / 扫码登录页 | 抖店扫码登录、抖音开放平台 OAuth |
| **Fetch 取数** | 读销量、评论、播放量 | 开放平台接口 / 商家后台页面 | 抖店商品分析、创作平台作品数据 |
| **Publish 发布** | 发视频、发商品 | 开放平台接口 / 发布页 | 抖音视频发布、抖店商品创建 |

**先分类，再谈实现。** 三类走的技术路径完全不同：

- 授权 → 必须用户在场，程序只负责"引路"
- 取数 → 能调接口就不碰页面
- 发布 → 接口优先，且**最后一步必须人工确认**

---

## 2. 页面地图（Page Map）

现在的 `sites.json` 只有一个 `loginUrl`，远远不够。要扩展到**每种用途一个页面**：

```jsonc
{
  "id": "douyin-shop",
  "name": "抖店",
  "authMode": "qrcode",              // oauth / qrcode / password(禁用)
  "dataAccess": "openapi",           // openapi / backend-api / page
  "pages": {
    "auth": {
      "url": "https://fxg.jinritemai.com/",
      "successWhen": "url-contains:/home",
      "expiresInDays": 30
    },
    "sales": {
      "url": "https://fxg.jinritemai.com/ffa/mshop/goods/list",
      "successWhen": "element:#goods-table",
      "requires": ["auth"]
    },
    "comments": {
      "url": "https://fxg.jinritemai.com/ffa/morder/comment/list",
      "successWhen": "element:#comment-list",
      "requires": ["auth"]
    }
  }
}
```

四个字段的含义：

| 字段 | 作用 |
|---|---|
| `url` | 具体到页面，不是网站首页 |
| `successWhen` | **怎么判断这一步成功了**（URL 变化 / 元素出现） |
| `requires` | 依赖哪一步先完成 |
| `expiresInDays` | 授权多久后要重新做 |

> 没有 `successWhen` 的页面登记等于没登记——程序不知道"到位了没有"。

## 3. 授权：三种形态，都要落到具体页面

| 形态 | 适用 | 落地页 | 成功信号 |
|---|---|---|---|
| **OAuth 授权码** | 有开放平台的（抖音开放平台、抖店开放平台） | 平台的授权页 | 本地回调收到 `code` |
| **扫码登录** | 商家后台（抖店、创作服务平台） | 后台登录页 | 登录后跳转到首页 / 出现用户头像 |
| **账号密码** | ❌ 不使用 | — | — |

### 3.1 OAuth 的落地细节

```
[1] 程序生成授权 URL（带 state 防 CSRF）
[2] 用系统默认浏览器打开这个 URL
[3] 用户在抖音/抖店页面上自己登录 + 点「授权」
[4] 平台回调 http://127.0.0.1:<随机端口>/oauth/callback?code=...
[5] 服务端用 code 换 access_token，加密入库
[6] 界面弹出「授权成功，可以继续」
```

`state` 必须校验，否则等于把回调接口开放给任何人。

### 3.2 扫码登录的落地细节

```
[1] 程序打开抖店登录页（系统浏览器或内嵌 WebView）
[2] 用户扫码
[3] 程序轮询「是否已登录」——判据是页面上的某个元素，不是猜
[4] 成功后落一个本地标记（含 expiresAt），关闭提示
```

**轮询判定必须基于页面事实**（URL 或元素），不能按"等 30 秒就算成功"。

## 4. 打开页面的三种方式（按优先级）

| 方式 | 何时用 | 优点 | 代价 |
|---|---|---|---|
| **系统默认浏览器** | 首选 | 兼容性最好、平台风控友好 | 会跳出应用 |
| **内嵌 WebView** | 平台明确允许时 | 不跳出、体验连贯 | 部分平台判为风险，可能封号 |
| **可见的 Playwright 窗口** | 需要页面操作时 | 能自动化 | 慢、易碎、必须让人看见 |

**默认用系统浏览器。** 内嵌只在确认平台允许时使用。

---

### 4.1 自动化分级（默认不自动化）

| 级别 | 程序做到哪一步 | 适用 | 硬约束 |
|---|---|---|---|
| **A0 仅直达** | 只打开页面 | 登录授权、支付、下单、删除、改权限 | — |
| **A1 辅助自动化** | 完成界面操作，**最后一步人点** | 发布视频/商品、上传素材 | 有头窗口 + 人工确认 |
| **A2 全自动读取** | 自动翻页采集 | 无副作用的列表读取 | 限速、单账号串行、可随时叫停 |

**顺序仍是：官方接口 > 后台内部接口 > 页面自动化。** 自动化不是第一选择，是接口走不通时的兜底。

> 「发布视频」属于 A1：程序可以把文件放好、标题填好、封面选好，但**「发布」那一下必须人点**。
> 这既是平台规则的要求，也是 `docs/11` 红线 1 的要求。

## 5. 数据从哪来：三级优先

```
① 开放平台 API      —— 稳定、合规、有文档
② 商家后台内部接口    —— 登录态下可调，随改版变动
③ 页面自动化抓取      —— 最后手段，必须限速且窗口可见
```

**每一级都要在页面地图里标明**（`dataAccess` 字段），界面也要如实告诉用户当前走的是哪一级。

## 6. 把你的例子逐条落地

需求原文：

> 查看店铺每天的销量以及评论，查看发布的短视频有多少播放量、点赞量、收集评论。

### 6.1 拆解成 5 个动作

| # | 需求 | 网站 | 具体页面 | 优先方式 | 降级 |
|---|---|---|---|---|---|
| 1 | 店铺每日销量 | 抖店 | 商品分析 / 交易概况 | 抖店开放平台 API | 后台页面读表格 |
| 2 | 店铺评论 | 抖店 | 评价管理 | 抖店开放平台 API | 后台页面翻页 |
| 3 | 短视频播放量、点赞量 | 抖音创作服务平台 | 作品数据 | 抖音开放平台 视频数据接口 | 创作平台页面 |
| 4 | 收集短视频评论 | 抖音 | 内容评论 | 抖音开放平台 评论接口 | 内容页滚动读取（限速） |
| 5 | （后续）发布视频 | 抖音创作服务平台 | 发布页 | 抖音开放平台 发布接口 | 页面自动化 + 人工确认 |

### 6.2 这个技能在程序里长什么样

**第一步：授权**（界面上的样子）

```
技能：店铺经营日报
需要授权：
┌────────────────────────────────────────────┐
│ 抖店      ● 未授权                          │
│ 用途：读取商品销量、评价                     │
│ [ 去授权 ]  ← 点击后打开抖店登录页           │
└────────────────────────────────────────────┘
┌────────────────────────────────────────────┐
│ 抖音创作服务平台   ● 已授权（30 天后过期）    │
│ [ 重新授权 ]                                │
└────────────────────────────────────────────┘
```

**第二步：取数**（每个数字都要能说清来源）

| 指标 | 来源 | 调用 |
|---|---|---|
| 日销量 | 抖店开放平台 | `GET /goods/sales?date=...` |
| 新增评价 | 抖店开放平台 | `GET /comment/list?date=...` |
| 播放量 / 点赞 | 抖音开放平台 | `GET /video/data?item_ids=...` |
| 评论内容 | 抖音开放平台 | `GET /comment/list?item_id=...` |

**第三步：取不到时降级**

```
检测到抖店开放平台未开通「评价」权限
→ 提示：可改用「后台页面读取」，需要保持窗口可见并限速
→ [ 改用页面读取 ]  [ 取消 ]
```

### 6.3 每个网站要登记的最小页面集

| 网站 | 必须登记的页面 |
|---|---|
| 抖店 | 登录页、商品分析页、评价管理页 |
| 抖音创作服务平台 | 登录页、作品数据页、发布页、评论管理页 |
| 抖音（内容端） | 内容页（读公开评论时用） |

## 7. 授权状态机与凭证

```
未授权 → 授权中 → 已授权 → 已过期 → 需重新授权
                    ↓
                  已撤销
```

| 项 | 做法 |
|---|---|
| 凭证存哪 | **本地加密**，Windows 用 DPAPI / 凭据管理器；不上传服务器 |
| 过期判定 | `expiresAt`（授权时记录）+ 接口返回的鉴权错误码，两者取先到 |
| 撤销 | 用户点「取消授权」删本地凭证；平台侧需用户自己去撤销 |
| 日志 | 只记录"某站点授权成功/失败/过期"，**不记录 token 值** |

## 8. 界面落地（具体到控件）

| 位置 | 元素 | 行为 |
|---|---|---|
| 技能部署页 · 方案卡 | 每个站点一个卡片 | 显示状态与「去授权 / 重新授权」 |
| 授权卡片 | 状态点 | 灰=未授权、黄=授权中、绿=已授权、红=已过期 |
| 授权卡片 | 「去授权」 | 打开该站点的 `pages.auth.url` |
| 授权中 | 轮询 | 每 2 秒判定一次，最长 5 分钟 |
| 超时 | 提示 | 「没有检测到登录成功，可点这里重新打开页面」 |
| 已过期 | 文案 | 「授权已于 X 月 X 日过期，请重新授权」 |

**所有状态都必须有界面表现**，不能只有一个转圈。

---

## 9. 失败与降级

| 情况 | 处理 |
|---|---|
| 平台改版，选择器失效 | 多候选选择器 + 失败截图 + 「改用人工」按钮 |
| 无 API 权限 | 降级为页面读取，并明确提示"窗口要保持可见" |
| 用户中途关闭页面 | 任务挂起，下次进来可续，不判失败 |
| 触发风控 / 验证码 | **立即停止**，提示用户手动完成，不尝试绕过 |
| 凭证过期 | 回到「需重新授权」，不重试到死 |

## 10. 合规红线

| 红线 | 说明 |
|---|---|
| 不代注册 | 账号必须是用户自己的 |
| 不代填密码 | 程序只打开页面，输入由用户完成 |
| 不绕验证码 | 遇到就停 |
| 页面自动化必须可见 | 不允许无头批量操作 |
| 单账号串行 | 不做多账号轮换 |
| 不采集他人数据 | 只读用户自己店铺/自己的作品 |
| 发布必须人工确认 | 机器准备，人点最后一下 |

## 11. 实施阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S1** | `sites.json` 扩展成页面地图，界面能列出"需要授权哪几个站点、哪些页面" | 方案卡显示站点与页面清单 |
| **S2** | 扫码登录打通（先抖店）：打开登录页 → 轮询判定 → 写入本地凭证 | 扫码后卡片变绿，重启仍有效 |
| **S3** | 数据接口对接：日销量、评论、播放量、点赞 | 每个指标能显示来源 |
| **S4** | 页面自动化兜底（无 API 权限时） | 可见窗口 + 限速 + 失败截图 |
| **S5** | 发布链路（人工确认） | 发布前必须点确认 |

**S2 是关键路径**——没有授权，后面全是空谈。
