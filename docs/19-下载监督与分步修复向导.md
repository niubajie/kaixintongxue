# 全流程下载监督与分步修复向导 · 技术方案

> 所属模块：本地资料（library）· 外网搜集 / 定时任务 / 网站设置
> 版本 v1.0 ｜ 2026-11-27 ｜ 状态：已实现并通过实测
> 解决问题：站点失效、弹窗、验证码、登录墙导致「搜不到就退出」「修一次就放弃」「第二次开始不再修复」。

---

## 0. 一句话

把「一次性的搜索下载」升级为「**全程有人盯、出异常随时进修复、修好自动接着下**」的闭环：
监督程序盯住下载进度，停滞就让执行流进入修复；修复向导在有头浏览器里分步处理弹窗/验证码/登录，
产出**经过真实下载校验**的结果后唤醒下载循环，继续落盘，绝不伪造成功。

## 1. 设计目标（与历史问题一一对应）

| 历史问题 | 本方案对策 |
|---|---|
| 修一次失败就退出 | `runScheduleSite` 改为修复循环，任务保持 `running`、停在 `phase=repair`，不终结 |
| 遇到弹窗/验证码没检测到真实下载就退出 | 打开先关弹窗、提交后校验结果真出现、识别验证码给明确 `failureCode`，结果必须过真实下载校验 |
| 第二次点「开始」不再修复 | 每轮 `bumpRunNonce`，事项带 `issueNonce`，前端去重键含 nonce 且点开始重置 |
| 「一直搜索中」不报错、不前进 | 每步硬超时 + 4 分钟整体看门狗，任何卡顿必带提示收尾 |
| 已收录资料被当成失败空转 | 结果回流但无新增时以 `nothing_new` 明确收尾 |

## 2. 总体架构

```
前端(桌面/Web 同源)
  │  点开始 / 暂停 / 修复向导操作
  ▼
schedule handler ──► runScheduleTask（一轮任务，单实例去重）
                          │ 启动 runScheduleSupervisor（监督 goroutine）
                          ▼
                     runScheduleSite（单站）
                          │  搜索→下载；0 新增或停滞 → 修复循环
                          ▼
              verifySiteDownloadable（无头自动验证）
                          │  失败/需登录
                          ▼
              publishIssue(issueNonce, failureCode) ──► 前端弹分步向导
                          ▼
              site_assist 会话（有头 Edge，单 goroutine 持上下文）
                          │  关弹窗→定位搜索→提交→校验→验证结果页
                          ▼
              storeAssistResults(可用结果) ──► 唤醒 waitForAssistResults
                          ▼
              downloadResults → insertPending → downloadIntoLibrary（落盘 + collected 递增）
```

## 3. 核心状态机

### 3.1 任务运行阶段（内存 `scheduleRuns`）

- `search`：常规搜索/下载中。
- `repair`：进入修复循环，任务保持运行，等待修复结果。
- `download`：正在把结果写入资料库。
- 运行结束删除该键；`instant` 任务结束同时把 `enabled` 置 0。

### 3.2 修复向导会话状态（`SiteAssistSnapshot.state`）

```
starting → awaiting_open → detecting_search → searching
   │            │               │                │
   │            │               │                ├─ awaiting_entry_choice（找不到搜索框）
   │            │               │                ├─ awaiting_search_url（用户补地址）
   │            │               │                ├─ login_waiting → login_verifying（需登录）
   │            │               │                ├─ ready（已验证可下载）
   │            │               │                └─ failed（带 failureCode）
   └─ closed（浏览器关闭/取消）
```

`ready` 且关联了任务时，结果写入 `scheduleAssistResults` 并关闭等待通道，下载循环被唤醒。

## 4. 全流程监督程序

- 每 8s 读一次该任务累计下载数 `collected`（以数据库为唯一真实来源）。
- 任务在跑、预算未耗尽、当前有在处理站点、且不在 `repair` 阶段时：
  - `collected` 连续 45s 不增长 → 判定停滞，`requestRepair(scheduleID)` 置位，并 `publishIssue(..., failureCode=stall)`。
- `runScheduleSite` 在「每条查询之间 / 每条结果之间」协作式检查 `repairRequested`，命中即让出进入修复，避免强杀正在进行的下载。
- 已在 `repair` 时不叠加触发，防止惊群。

## 5. 修复循环（不再一次失败就退出）

单站进入修复循环后：

1. 先无头自动验证 `verifySiteDownloadable`（90s 超时，最多 2 次），覆盖「风控恢复 / 换关键词命中」等简单可恢复场景；需登录则直接跳出自动尝试。
2. 自动验证通过 → 重跑常规检索；仍无新增 → 升级人工向导。
3. 升级人工向导：`publishIssue` 带自增 `issueNonce` 与 `failureCode`，前端据此弹向导；此处**阻塞** `waitForAssistResults`（15s 粒度、可被暂停/取消打断）。
4. 拿到向导交付的真实结果：
   - 有新增下载 → 清事项、回 `search`，继续；
   - 无新增（多为去重命中/无法下载）→ 再跑一次常规检索，仍无则以 `nothing_new` 明确收尾，不空转。
5. 连续多轮仍无真实下载 → `exhausted` 收尾；向导被关且未交付时由 `reopenAssist` 自动重开（上限 4 次）。

## 6. 弹窗 / 验证码 / 登录处理（关键健壮性）

- **关弹窗**：`assistDismissPopupsScript` 只用特征选择器（`[role=dialog]`、`[class*=modal/dialog/popup/mask/cookie/consent/notice]` 等）并限量（容器≤30、内部节点≤25），**禁止遍历 `body *`**——旧实现逐元素取样式在大页面会卡死主线程，这是「一直搜索中」的根因之一。
- **提交校验**：提交后比较 URL 与结果链接数，未变化则换「点搜索按钮 / 回车」重试；受控输入走原生 `value setter` 再派发 `input/change`，保证 React/Vue 受控框生效。
- **验证码/登录墙识别**：`assistDetectBlockerScript` 扫描正文与 iframe 特征（验证码/安全验证/人机验证/recaptcha/geetest/password 框），命中给出 `failureCode=captcha`，引导用户在同一窗口完成后点「重新修复」。
- **结果页验证**：`probeDownloadable`（8s 超时）判直链；否则在同一会话导航结果页抽正文。验证完**直接导航回搜索列表页**（不再用 `NavigateBack`，后者会被 beforeunload 挂住，是第二个卡死根因）。
- **硬超时全覆盖**：关弹窗 8s、识别 12s、提交 30/35s、提取 12s、结果页 18s、回退 10s；外加 4 分钟整体看门狗，超时必带 `failureCode=timeout` 收尾，绝不静默。

## 7. 接口契约

任务事项字段（`GET /api/library/schedules` 返回）：

| 字段 | 含义 |
|---|---|
| `issueKind` | `login` / `failed` |
| `issueSiteId` / `issueMessage` | 出问题的站点与提示 |
| `issueFailureCode` | `no_download` / `stall` / `captcha` / `no_results` / `no_search_box` / `submit_blocked` / `no_usable` / `nothing_new` / `exhausted` / `timeout` |
| `issueNonce` | 运行/重试序号，新一轮自增，前端据此区分「同一错误的新一轮」 |

修复向导接口（本地 sidecar，不入 openapi.yaml）：

```
POST /api/library/sites/assist/start         开启/复用会话（siteId, keyword, scheduleId）
GET  /api/library/sites/assist/status        轮询会话快照
POST /api/library/sites/assist/open          用户反馈能否打开
POST /api/library/sites/assist/search-entry  decision: advanced/provideUrl/unsupported
POST /api/library/sites/assist/search-url    用户补搜索页地址（写回 search_sites.domain）
POST /api/library/sites/assist/login         主动进入登录等待
POST /api/library/sites/assist/login-confirm 用户确认已登录
POST /api/library/sites/assist/retry         同一浏览器窗口内重搜（保留验证码/登录状态）
POST /api/library/sites/assist/cancel        关闭会话；giveUp=true 才彻底放弃本站
```

## 8. 双端前端交互（桌面 / Web 同源）

- 监听 `schedules` 出现 `issueSiteId` 即弹分步向导；去重键 = `taskId:issueSiteId:issueNonce:issueMessage`，**含 nonce**，故同一错误的新一轮仍会弹。
- 点「开始」时清空去重标记，保证每次手动开始都能重新进入修复。
- 失败态按 `failureCode` 给针对性提示，并提供「重新修复 / 修改搜索页地址 / 此站需要登录 / 放弃本站」。
- 向导打开时记录 `collected` 基线，之后真实增长即判定下载恢复；`ready` 后自动关窗并关浏览器。

## 9. 数据一致性与「不伪造成功」

- 落盘唯一入口 `insertPending`：先按 `url/fingerprint` 去重与拉黑，再 `downloadIntoLibrary` 真实下载/正文落盘，成功才 `collected+1`。
- 向导交付的结果若全部去重命中或下载失败，`collected` 不增，任务以 `nothing_new` 如实收尾，**不计为新增、不谎报成功**。
- 资料仍进 `pending_docs` 待审核，沿用既有审批/归库链路。

## 10. 实测结论（sidecar 实测）

| 场景 | 结果 |
|---|---|
| 问题站 `1.xiang810.cc:88/search` 修复 | 约 14s 到 `ready`，期间显示「正在验证第 x/y 条」，不再卡死 |
| 结果回流唤醒下载 | 会话带 `scheduleId`，提示「正在恢复原搜索任务」，任务被唤醒 |
| 已收录资料 | 以 `nothing_new` 收尾：「均已在库中或无法下载」，任务正常结束，不空转 |
| 第二次点「开始」 | `issueNonce` 递增（2→4），事项重新发布，向导再次弹出 |
| 构建 | `gofmt` 干净、`go vet` 通过、`go test -race` PASS、双端 `typecheck`+`build` 通过 |

## 11. 已知限制与后续

- 监督基于 `collected` 增量，纯「留言」类站点在合并写文档前不增数，长任务可能误报停滞；后续可按站点类型细化判据。
- 验证码仍需人工在同一窗口完成，不做自动识别打码。
- `exhausted`/`nothing_new` 后需用户换关键词或确认站点有货再开始。
- 修复会话存内存，sidecar 重启后需重新开始。
